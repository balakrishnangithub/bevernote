# ENEX and ENML compatibility

## Import

Bevernote reads standard Evernote `.enex` XML exports one note at a time. For each note it preserves:

- title, created/updated timestamps, tags, and Evernote GUID;
- note attributes, including repeated and non-string values;
- original ENML content, including CDATA;
- resource bytes, MIME type, dimensions, duration, recognition XML, resource attributes, and alternate resource data;
- embedded OCR text in the local full-text index.

Resources receive new local database IDs, while their content hashes and Evernote media references are retained. A deterministic fingerprint over the imported source, metadata, tags, and resources prevents exact duplicate notes on repeated imports. The Evernote GUID is included when available but is not used alone, so distinct notes sharing a GUID remain valid. An exact reimport never overwrites local edits. Known `evernote:///view/...` links are rewritten to local `bevernote://note/...` links after import.

When offline OCR is enabled (the default), PNG, JPEG, and WebP resources without Evernote recognition data are processed on the device using bundled Ocrs models. Recognized text is added to the local FTS5 resource index. Original images and ENML remain unchanged, existing recognition data wins, and recognition failures produce a warning rather than failing the import. The early-preview models primarily support the Latin alphabet; handwriting and non-Latin scripts may be inaccurate. Models are CC BY-SA 4.0 licensed with attribution in `crates/bevernote-core/models/README.md`.

## Editing and export

Imported notes have two related representations:

1. `original_enml`, the imported source;
2. `content_html`, the editable TipTap representation.

If the note has not changed its editable content, export writes the original ENML. After editing, export serializes the current editor document as ENML and retains the original separately in the local database for provenance. Original ENML retention is not a promise that every arbitrary edit can be represented identically in Evernote.

Classic `en-todo`, `en-media`, and `en-crypt` nodes have custom editor representations. Modern `--en-todo` / `--en-checked` checklist styles are normalized into editable task items. `en-crypt` payloads are preserved but not decrypted.

## Known boundaries

- Import memory is bounded by the current note and its largest attachment, not constant.
- Very large single resources should be handled with a streaming decoder in a future optimization.
- OCR currently targets Latin-alphabet PNG, JPEG, and WebP images; handwriting and other scripts may be inaccurate. OCR images larger than 40 MB are skipped, and large images are downscaled to at most 2200 pixels per dimension for inference.
- Encrypted-block decryption is not implemented.
- Some Evernote-specific presentation attributes may be normalized by the editor after an actual edit.
- Standard HTML generated by the editor is not guaranteed to reproduce every proprietary Evernote rendering behavior.

## Regression strategy

Unit tests cover CDATA, XML entities, multiple notes, attachments, attributes, duplicate GUIDs, internal links, checklists, and unchanged ENML export. The `verify_enex` example additionally imports a real file, exports all imported notes, reimports the result, and compares source ENML, metadata, attachment hashes, and offline title search.

```sh
cargo run -p bevernote-core --example verify_enex -- path/to/input.enex path/to/new-empty-work-directory
```

Private ENEX samples belong in ignored `test-data/`; never commit them.
